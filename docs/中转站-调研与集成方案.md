# 局域网「文件中转站」调研与集成方案

> 目标：在已有零依赖 Node 图库服务（`server.js`，单文件，`0.0.0.0:8710`，原生前端）里加一个
> 「电脑拖文件进网页 → 同 WiFi 手机打开同一地址 → 看到列表 → 自行下载 → 下完删 / 留 N 小时」的功能。
>
> 现有可复用资产：`sendFile()`（已实现 `Range`/`206`/`416`/`ETag`/`Accept-Ranges`）、
> `readBody()`、`sendJSON()`、`fail()`、`lanAddresses()`、`resolveSafe()`、`servePublic()`。

---

## 0. 结论前置

1. **不要做 WebRTC**。同一 WiFi 下 WebRTC 的唯一收益是「不落盘」，代价是 SDP 信令、STUN、
   TURN 兜底、双端必须同时在线、iOS 后台挂起。你已经有 HTTP 服务，纯 HTTP 上传下载在
   LAN 内是 30–90 MB/s 的量级，比 WebRTC 数据通道更稳。
2. **不要做 multipart**。`File` 本身就是 `Blob`，`fetch(url, {body: file})` 直接发裸字节，
   `Content-Length` 由浏览器自动带上，服务端 `req.pipe(ws)` 就完事。multipart 解析器是这类
   项目 80% 的 bug 来源（boundary 跨 chunk 边界、CRLF、epilogue），可以整块砍掉。
3. **不要照抄 LocalSend 的 HTTPS**。它自己在协议文档里写明：反向下载 API 必须走**明文 HTTP**，
   因为浏览器拒绝自签证书。这句话直接否定了「手机浏览器做接收端 + TLS」这条路。
4. 真正要抄的是 **Mozilla Send 的三件套**：密文/文件落盘、`#` 片段存密钥（不发往服务端）、
   **时间 + 次数双闸门**。这是「中转站」的本质模型，比 P2P 简单一个数量级。
5. 唯一必须自己写、且必须写对的：**上传的背压与中断续传**，以及 **`Content-Disposition` 的中文名编码**。

## 1. 横向对比

| 项目 | 传输通道 | 设备发现 | 加密 / 鉴权 | 依赖体量 · 能否零依赖复刻 | 关键取舍（一句话） |
|---|---|---|---|---|---|
| **LocalSend**（Flutter/Dart） | 纯 HTTP REST：`POST /api/localsend/v2/prepare-upload` → `POST /upload?sessionId&fileId&token` 发裸二进制；反向 `GET /download` | UDP 组播 `224.0.0.167:53317` 广播 + `POST /register` 双向应答；失败回落「遍历所有内网 IP 打 register」 | 默认 HTTPS 自签证书，`fingerprint` = 证书 SHA-256；可选 6 位 PIN（`?pin=`） | Flutter 运行时（几十 MB）。**协议本身可零依赖复刻**：发送端约 200 行 Node 即可 | 协议极简、无服务器，但**要求对端装 App**；浏览器只能当「下载端」，且明文 HTTP |
| **PairDrop**（Web，Snapdrop 后继） | WebRTC DataChannel 直连；NAT 打洞失败走 TURN 中继（密文，TURN 读不到内容） | 同公网 IP 自动可见；房间码；配对（IndexedDB 长密钥，服务端只比对）；二维码 | WebRTC 强制 DTLS-SRTP E2E；服务端只见 SDP | Node + `ws` + express，服务端很小，但**必须部署 STUN/TURN**。零依赖可复刻信令（RFC6455 手搓约 150 行），TURN 不可 | 真 P2P 体验标杆，代价是「双端在线 + 信令 + TURN + 浏览器兼容矩阵」四座山 |
| **Snapdrop**（原版） | WebRTC + PeerJS 公共 broker | 同公网 IP | 同 PairDrop | 同上，且已基本停更 | 证明了「同网段自动发现」的体验价值，也证明了它的天花板 |
| **croc**（Go，CLI） | 先 TCP 中继（9009–9013），握手后尝试 Tailcat/WireGuard 直连 UDP；`croc store` 是加密落盘 + 链接 | 无发现：**三词口令**（`croc send` 打印，对端 `croc 口令`）；`--qr` 出二维码指向 web 客户端 | PAKE（SPAKE2，NIST 曲线）派生会话密钥 + AES-GCM；口令即密钥材料 | 单二进制。**不可零依赖复刻**：`node:crypto` 没有 SPAKE2，手写等于自己实现密码学 | 「任何两台机器」的极致，代价是必须装二进制；口令强度即安全性上限 |
| **magic-wormhole**（Python） | mailbox 服务器（交换 SPAKE2 消息）+ transit relay（TCP 直连失败时中继） | 无发现：`7-crossover-clockwork` 式人类可读口令，一次性 | SPAKE2 + NaCl secretbox；服务器只做信箱，不知道口令 | 不可零依赖复刻（同 croc） | 「口令配对」的开创者，把「服务器零知识」做成了范式 |
| **Wormhole William**（Go） | 同 magic-wormhole，**线协议兼容** | 同上 | 同上 | 不可 | 证明了该协议可被独立实现 → 协议稳定，但仍是 CLI 世界 |
| **sendme**（Rust / iroh） | QUIC + TLS 1.3；打洞优先，失败走 relay | 无发现：`ticket`（32 字节 node id，IP 变了仍有效） | TLS 1.3 + BLAKE3 内容校验 | 不可 | wormhole 的现代版：**内容寻址 + 可验证流式**，天生支持断点续传（BLAKE3 verified streaming） |
| **ShareDrop**（原版 / sharedrop.org） | WebRTC DataChannel；同网直连 → 公网打洞 → TURN 中继三级降级 | 房间码 / 链接 / 二维码 / 6 位短码；**6 位安全码**（DTLS 证书指纹派生，人工比对防中间人） | WebRTC E2E + 可选安全码验证 | 前端 + 信令，需 TURN | 浏览器端体验天花板：64 KiB 分块 + 流控 + SHA-256 + 断点续传 + 逐级降级，也演示了「大文件在浏览器里的真实上限」（Chrome 桌面可流式落盘，Firefox/Safari 内存兜底 512 MB 封顶） |
| **Mozilla Send**（Firefox Send，2020 停服；活跃 fork：`timvisee/send`） | **纯 HTTP 上传下载**，服务端只存密文 | 无发现：分享链接，密钥在 `#` 片段（浏览器不会把它发给服务器） | 客户端 WebCrypto AES-GCM 加密后再上传；服务端零知识；可选密码二次派生 | Node + Redis/Valkey + S3/本地盘。**「密文落盘 + 双闸门」子集可零依赖复刻** | 中转站的教科书：`下载次数 1–20` + `过期 1–7 天`，默认上限 2 GB；停服说明「公共免费中转」的运营成本才是真问题，而不是技术 |
| **Filebrowser**（Go） | 纯 HTTP（含 `Range` 流式播放） | 无（手动输地址） | JWT 登录；分享链接带过期时间与可选密码 | 单二进制（Docker 31 MB）。**「分享链接」子集可零依赖复刻**，文件管理器整体不可 | 把「临时分享」做成了「永久文件管理」，功能全但心智重 |
| **Filebrowser Quantum**（Go fork） | 同上 + WebDAV | 无 | OIDC / LDAP / JWT / 密码+2FA / 代理认证 | 单二进制（Docker 180 MB），SQLite 索引，最低 256 MB 内存 | 证明了「分享 = 过期时间 + 谁能访问 + 读写权限」这三元组就够用，不需要账号体系 |
| **Gokapi**（Go） | 纯 HTTP | 无 | 管理员登录 + 分享链接 | 单二进制 | 极简版 Send：只有「过期 / 下载次数 / 自毁」，恰好是你要的全部 |
| **Node 生态最小实现**（`node:http` + `fs.createWriteStream`） | 纯 HTTP | 无 | 无 / token | **零依赖**。`multer` = express 中间件 + `busboy`；`busboy` 才是真正的 multipart 状态机；`formidable` 是另一实现 | 三者解决的唯一问题是「boundary 跨 chunk」。既然可以不用 multipart，这三个包就都不需要 |
| **tus 协议**（`tus.io`，IETF draft） | 纯 HTTP | 无 | 无（鉴权由应用层加） | 协议规范，**零依赖可实现子集** | 断点续传的唯一事实标准：`HEAD` 读 `Upload-Offset` → `PATCH` 带 `Upload-Offset` 追加；`Tus-Resumable: 1.0.0` |

### 读表后的四条硬结论

- **想让「手机浏览器」当接收端**，就必须是纯 HTTP，且必须是明文（或真证书）。LocalSend 的协议文档
  自己承认了这一点（"browsers reject self-signed certificates"），所以它的反向 API 走 HTTP。
- **「同一 WiFi」这个前提，让 WebRTC 的全部复杂度都变成了净亏损**：打洞在同网段本来就直接通，
  但你仍然要付信令、TURN、双端在线、iOS 挂起的代价。
- **中转站 ≠ P2P**。P2P 省的是磁盘，中转站省的是「两端同时在线」这个约束。你的场景（手机后来才打开）
  天然需要落盘，所以直接选落盘模型，别绕。
- **能砍的只有一个东西：multipart**。砍掉它，零依赖 Node 的上传代码从 ~200 行降到 ~15 行。

## 2. A. 三个技术方案（复杂度从低到高）

三个方案共用同一套「元数据先建会话、再传字节」的两段式，这是 LocalSend `prepare-upload` 和
tus `POST` 的共同做法，好处是**服务端在收第一字节之前就知道文件多大、叫什么、能不能收**。

### 方案 1（低）· 裸 body 单请求直传

| 维度 | 做法 |
|---|---|
| **上传** | `fetch('/api/drop/'+id, {method:'PUT', body: file})`。**无 multipart**，`body` 直接是 `File`（`Blob`），浏览器自动带 `Content-Length`。元数据走 `POST /api/drop` 的 JSON body（`{name,size,type,ttl,once}`）。服务端 `req.pipe(fs.createWriteStream(part))`。 |
| **进度** | 客户端用 `XMLHttpRequest`（**`fetch` 没有上传进度**）：`xhr.upload.onprogress` → `e.lengthComputable / e.loaded / e.total`。服务端不需要进度。 |
| **断点续传** | 不做。失败即重传整个文件。 |
| **文件列表** | 内存 `Map<id, meta>` 为准，`drops/index.json` 落盘（写操作 300 ms 防抖后整体重写，几 KB 而已）。启动时读回。 |
| **清理** | `setInterval(sweep, 60_000)` 比对 `expiresAt`；`timer.unref()` 让进程能正常退出。删除 = `fs.unlink` + 从 Map 摘除 + 重写 index。 |
| **安全边界** | ① `req.socket.remoteAddress` 同网段校验（私有网段 + 前三段相同）；② 每个 drop 一个 `crypto.randomBytes(16).toString('base64url')` token，出现在列表/下载 URL 里，`crypto.timingSafeEqual` 比对；③ 单请求上限（`content-length` 必须等于声明 size）；④ 总量配额。 |
| **代码量** | 服务端 ~120 行，前端 ~80 行。 |

**适用**：文件普遍 < 500 MB、WiFi 稳定、能接受「断了重传」。**两小时能上。**

### 方案 2（中，推荐）· `Content-Range` 追加式续传 + SSE 实时列表

| 维度 | 做法 |
|---|---|
| **上传** | 仍然裸 body，但**分片**：`PUT /api/drop/:id`，头带 `Content-Range: bytes 0-4194303/20971520`，body 是 `file.slice(start,end)`（4 MiB 一片）。服务端读 `.part` 的 `stat().size`，**等于 `start` 就 `flags:'a'` 追加**，不等就 `409 {"expect": 实际字节数}`，客户端从该偏移续传。这是 tus 的语义，但只用了 `Content-Range` 一个头。 |
| **进度** | 双层：单片内用 `xhr.upload.onprogress`，跨片用「已完成字节 / 总字节」累加。服务端顺带把 `received` 记进 meta，页面刷新后能显示「已收 37%」。 |
| **断点续传** | **要**，而且是字节级。iOS 切后台被挂起、WiFi 抖动、手机锁屏，都靠它救。 |
| **文件列表** | 同方案 1（`Map` + `index.json`），但多一个 `received` 字段。 |
| **清理** | 同方案 1，外加：`once: true` 时在 `res.on('finish')` 后 `setTimeout(remove, 2000)`（Windows 上 ReadStream 句柄释放有延迟，立刻 unlink 会 `EBUSY`）。 |
| **安全边界** | 同方案 1，外加 `PUT` 的 `total` 必须等于会话声明的 `size`（防止用续传口子往磁盘里灌任意大小）。 |
| **实时列表** | `GET /api/drop/events` → `text/event-stream`，`res.flushHeaders()`，新文件/删除时 `res.write('data: '+JSON.stringify(list)+'\n\n')`，15 s 一次 `: ping\n\n` 心跳。手机端比轮询省电，比 WebSocket 少一个 `ws` 依赖。 |
| **代码量** | 服务端 ~250 行，前端 ~150 行。 |

**适用**：这就是你的场景。**推荐它。**

### 方案 3（高）· tus 子集 + 二维码 + PIN + 配额 LRU

| 维度 | 做法 |
|---|---|
| **上传** | 完整 tus 子集：`POST /files`（`Upload-Length`、`Upload-Metadata`）→ `201` + `Location`；`HEAD /files/:id` → `Upload-Offset`；`PATCH /files/:id`（`Upload-Offset` + `Content-Type: application/offset+octet-stream`）追加。全部响应带 `Tus-Resumable: 1.0.0`。 |
| **进度** | 同上；另可加 `HEAD` 轮询做「多设备同步进度」。 |
| **断点续传** | 有，且是标准协议，将来能接任何 tus 客户端（比如 `tus-js-client`、rclone）。 |
| **文件列表** | 磁盘 JSON + 内存缓存；加 `sha256` 字段（`crypto.createHash('sha256')` 边收边算），下载端可校验。 |
| **清理** | TTL + **总字节配额 LRU**（超配额时按 `lastAccess` 淘汰最旧）+ `once` 自毁。三闸门。 |
| **安全边界** | 同方案 2 + 6 位 PIN（`timingSafeEqual`）+ **二维码**（零依赖 byte-mode QR 编码器约 250 行，输出 SVG；或退化成 `/d/ab12cd` 六位短码 + 大字号 URL）。 |
| **代码量** | 服务端 ~500 行 + 前端 ~300 行。 |

**适用**：要做成通用工具、或想被 rclone/tus 客户端直接对接。**对这个图库项目是过度设计。**

## 3. B. 推荐：方案 2

理由，按重要性排：

1. **它和「浏览器 + 手机 + 同一个 Node 进程」三者同时最契合**。
   - 浏览器：只用 `fetch` / `XHR` / `Blob.slice`，零 SDK、零信令、零证书。
   - 手机：`Content-Disposition: attachment` 一句话就让 iOS/Android 走「存储」而不是「打开」；
     不需要装 App，不需要扫 PairDrop 那种房间码。
   - 同一个 Node 进程：**不新增端口、不新增依赖**，直接挂在现有 router 上，
     下载侧 100% 复用已有的 `sendFile()`（`Range`/`206`/`416`/`ETag` 全部现成）。
2. **续传是必需品，不是加分项**。手机浏览器切后台几十秒就被挂起，2 GB 视频在 WiFi 5 上要 5–10 分钟，
   没有续传等于「大文件必失败」。而续传的全部成本只是「一个 `Content-Range` 头 + 一个 409 分支」，
   比上 WebRTC 便宜两个数量级。
3. **SSE 比 WebSocket 便宜，比轮询省电**。零依赖，一行 `res.write('data: ...\n\n')`，
   还能顺手解决「电脑上传完，手机页面自动刷新出列表」这个体验点。
4. **风险面最小**。没有 STUN/TURN 的运维、没有 TLS 证书、没有 P2P 打洞失败的长尾；
   失败模式只有「上传中断」和「磁盘满」，都可控。

**不推荐方案 1 的原因**：省下的 30 行代码，换来「大文件必失败」。
**不推荐方案 3 的原因**：tus 的标准化收益在这个私有场景里用不上；QR 编码器 250 行纯手写，
出错率高、收益（省一次手输 IP）不匹配。

## 4. C. 五个最容易踩的坑

### 坑 1 · iOS Safari 的后台上传被挂起 + `Content-Length` 丢失

- iOS 在切后台/锁屏后**很快（数十秒级）挂起 JS**，`xhr`/`fetch` 直接停摆，`fetch` 的 `keepalive: true`
  只有 **64 KB** 上限，救不了大文件。
- 更隐蔽：如果你图省事用 `fetch(url, {method:'POST', body: formData})` 且 body 是流
  （`duplex:'half'`），浏览器会改用 `Transfer-Encoding: chunked`，**`req.headers['content-length']` 变
  `undefined`**，服务端算不出百分比，进度条直接废。
- 对策：① 分片 + `visibilitychange` 事件里检查 `off < file.size` 就续传；
  ② 上传期间 `await navigator.wakeLock.request('screen')`（Safari 16.4+）防锁屏；
  ③ 元数据先走 `POST` 建会话，服务端从会话里拿 `size`，**不依赖 `content-length`**。

### 坑 2 · 大文件把内存撑爆（`readBody` 不能复用）

- 现有 `readBody()` 是 `Buffer.concat(chunks)` 全量缓冲，上限 262144 字节。**上传路径绝对不能调它**，
  否则 2 GB 文件直接 OOM（而且它的 `limit` 会先把你 413 掉）。
- 必须 `req.pipe(ws)`（`pipe` 自带背压）；并且要挂 `req.on('aborted')` / `ws.on('error')`，
  在中断时 `ws.destroy()`，**保留** `.part`（这是续传的原料），但要 `fs.unlink` 掉「从未开始」的会话。
- 下载侧反向同理：`fs.createReadStream().pipe(res)` 已由 `sendFile()` 正确处理；
  自己写的话若手动 `res.write(chunk)` 而不检查返回值，必须 `if (!res.write(c)) res.once('drain', next)`。

### 坑 3 · Node 默认 5 分钟掐断请求（`server.requestTimeout`）

- Node 18+ `server.requestTimeout` 默认 **300000 ms**。慢 WiFi 传 2 GB 必然超时，
  表现是「传到一半连接被重置 / 408」，而且**日志里什么都不明显**。
- 对策：`server.requestTimeout = 0;`（LAN 场景可接受），并给单请求加自己的尺寸上限做保护。
  `server.headersTimeout`（默认 60 s）保持不动即可。
- 顺带：客户端可能发 `Expect: 100-continue`。Node 在没有 `'checkContinue'` 监听器时会**自动回
  `100 Continue`**，不用管；一旦你自己监听了 `'checkContinue'`，就必须手动 `res.writeContinue()`，
  否则上传会卡死在等 100。

### 坑 4 · 中文文件名：`filename=` 只允许 ASCII

- 只写 `Content-Disposition: attachment; filename="报告.pdf"` → 多数浏览器得到乱码或 `download`。
  必须用 RFC 5987/6266 的扩展参数：
  `attachment; filename="fallback.pdf"; filename*=UTF-8''%E6%8A%A5%E5%91%8A.pdf`
- `encodeURIComponent` **不转义** `! ' ( ) *`，这几个字符会让部分解析器出错，要手动补：
  `.replace(/['()*]/g, c => '%' + c.charCodeAt(0).toString(16).toUpperCase())`。
- 反向（上传）同理：用 `x-filename: encodeURIComponent(name)` 传，服务端 `decodeURIComponent` 之后
  **必须** `path.basename()` + 过滤 `..` `/` `\` `\0` `:`，Windows 还要过滤 `<>"|?*` 和保留名
  （`CON PRN AUX NUL COM1 LPT1`）。否则一个叫 `..\..\server.js` 的文件就能覆盖你的源码。
- 磁盘上别用原名：存 `drops/<id>.bin`，原名只存在 JSON 里。这样既避免编码问题，也避免同名覆盖。

### 坑 5 · 手机端「打开」而不是「保存」

- iOS Safari 对 `Content-Type: image/jpeg` 会内联预览；`<a download>` 对跨源 URL 也常被忽略。
- 必须三件套：`Content-Type: application/octet-stream` + `Content-Disposition: attachment` +
  `X-Content-Type-Options: nosniff`（你已有）。想要缩略图预览就另开 `?inline=1` 走 `<img>`。
- 另：`Content-Length` 缺失时 iOS 的下载进度圈会一直转不结束——所以 `sendFile()` 里那行
  `Content-Length: total` 不能省；`206` 分支里的 `Content-Length: end-start+1` 同理。
- Chrome 桌面可 `showSaveFilePicker()` 流式落盘；Safari/Firefox 只能 `Blob` + `<a download>`，
  内存兜底，**单个文件 > 512 MB 在 Safari 上就是不行**（这是浏览器能力边界，不是你的 bug，界面上要提前说）。

### 附加（顺手会踩）

- `sendFile()` 的默认 `Cache-Control: public, max-age=31536000, immutable` **绝不能**用于 drop 文件
  （文件会被删/换）。传 `'no-store'`。
- 分片续传必须 `flags:'a'` 或 `{flags:'r+', start}`，默认 `'w'` 会**截断**已有数据。
- IPv6 客户端地址是 `::ffff:192.168.1.7`，做同网段判断前先 `replace(/^::ffff:/,'')`。
- Windows 首次监听会弹防火墙授权框；用户点了「拒绝」则手机永远连不上，且没有任何报错。
  启动时把 `lanAddresses()` 打印出来，并在页面上显示「手机打不开 → 检查防火墙」。
- 同网段判断别写死 `/24`：家庭网常见 `/24`，但 `/16`、`/22` 也有。退一步用「RFC1918 私有段 + 与任一
  本机网卡前三段相同」的双条件，比精确算掩码（Node 无 API）更实用。

```js
const DROP_DIR   = path.join(APP_DIR, 'drops');
const DROP_INDEX = path.join(DROP_DIR, 'index.json');

const DROPS = new Map();                   // id -> meta
let saveTimer = null;

function dropLoad() {
    try {
        fs.mkdirSync(DROP_DIR, { recursive: true });
        const raw = JSON.parse(fs.readFileSync(DROP_INDEX, 'utf8'));
        for (const d of raw) DROPS.set(d.id, d);
    } catch (e) { /* 首次启动没有索引，正常 */ }
}
function dropSave() {
    clearTimeout(saveTimer);
    saveTimer = setTimeout(() => {
        const arr = [...DROPS.values()].filter(d => d.ready);
        fs.writeFile(DROP_INDEX, JSON.stringify(arr), () => {});
    }, 300);
}
function dropRemove(id) {
    const d = DROPS.get(id);
    if (!d) return;
    DROPS.delete(id);
    for (const f of ['.bin', '.part']) {
        try { fs.unlinkSync(path.join(DROP_DIR, id + f)); } catch (e) { }
    }
    dropSave();
    dropBroadcast();
}
function dropSweep() {
    const now = Date.now();
    for (const d of DROPS.values()) if (d.expiresAt <= now) dropRemove(d.id);
}
const dropTimer = setInterval(dropSweep, 60_000);
dropTimer.unref();                          // 不阻塞进程退出

// 同网段判断（LAN 场景够用，别追求精确掩码）
function sameLan(req) {
    let ip = (req.socket.remoteAddress || '').replace(/^::ffff:/, '');
    if (ip === '127.0.0.1' || ip === '::1') return true;
    const m = /^(\d+)\.(\d+)\.(\d+)\.(\d+)$/.exec(ip);
    if (!m) return false;
    const a = +m[1], b = +m[2];
    const priv = a === 10 || (a === 172 && b >= 16 && b <= 31) || (a === 192 && b === 168);
    if (!priv) return false;
    return lanAddresses().some(x => {
        const r = x.ip.split('.');
        return +r[0] === a && +r[1] === b && +r[2] === +m[3];
    });
}

function safeName(name) {
    let n = String(name || 'file').split(/[\\/]/).pop();
    n = n.replace(/[\x00-\x1f<>:"|?*]/g, '_').trim();
    if (!n || /^(con|prn|aux|nul|com[1-9]|lpt[1-9])(\.|$)/i.test(n)) n = 'file_' + n;
    return n.slice(0, 180);
}

// RFC 5987：filename* 里的值
function rfc5987(s) {
    return encodeURIComponent(s).replace(/['()*]/g, c => '%' + c.charCodeAt(0).toString(16).toUpperCase());
}
```

```js
async function handleDropPut(req, res, id) {
    const d = DROPS.get(id);
    if (!d) throw fail(404, 'no such drop');
    if (!d.token || d.token !== (req.headers['x-token'] || '')) throw fail(403, 'bad token');

    const m = /^bytes (\d+)-(\d+)\/(\d+)$/.exec(req.headers['content-range'] || '');
    if (!m) throw fail(400, 'need Content-Range');
    const start = +m[1], end = +m[2], total = +m[3];
    if (total !== d.size) throw fail(400, 'size mismatch');
    if (req.headers['content-length'] !== String(end - start + 1)) throw fail(400, 'length mismatch');

    const part = path.join(DROP_DIR, id + '.part');
    let have = 0;
    try { have = (await fsp.stat(part)).size; } catch (e) { }
    if (have !== start) { sendJSON(req, res, 409, { expect: have }); return; }   // 让客户端自己对齐

    const ws = fs.createWriteStream(part, { flags: 'a' });   // 注意 'a'，不是默认的 'w'
    try {
        await new Promise((ok, no) => {
            req.on('aborted', () => { ws.destroy(); no(fail(499, 'aborted')); });
            ws.on('error', no);
            ws.on('finish', ok);
            req.pipe(ws);                                    // pipe 自带背压，不用手写 drain
        });
    } catch (e) {
        if (e.status === 499) return;                        // 客户端断了，.part 保留给续传
        throw e;
    }
    const now = (await fsp.stat(part)).size;
    if (now !== end + 1) throw fail(500, 'short write ' + now);
    sendJSON(req, res, 200, { offset: now });
}
```

```js
async function handleDropFinish(req, res, id) {
    const d = DROPS.get(id);
    if (!d) throw fail(404, 'no such drop');
    if (d.token !== (req.headers['x-token'] || '')) throw fail(403, 'bad token');
    const part = path.join(DROP_DIR, id + '.part');
    const st = await fsp.stat(part).catch(() => null);
    if (!st || st.size !== d.size) throw fail(409, 'incomplete ' + (st ? st.size : 0) + '/' + d.size);
    await fsp.rename(part, path.join(DROP_DIR, id + '.bin'));
    d.ready = true; d.createdAt = Date.now();
    d.expiresAt = d.createdAt + (d.ttl || DROP_TTL);
    dropSave(); dropBroadcast();
    sendJSON(req, res, 200, { ok: true, id });
}

function sendDropFile(req, res, d) {
    const abs = path.join(DROP_DIR, d.id + '.bin');
    fs.stat(abs, (err, st) => {
        if (err || !st.isFile()) { sendJSON(req, res, 404, { error: 'gone' }); return; }
        const ascii = d.name.replace(/[^\x20-\x7e]/g, '_').replace(/["\\]/g, '_');
        res.setHeader('Content-Disposition',
            `attachment; filename="${ascii}"; filename*=UTF-8''${rfc5987(d.name)}`);
        d.downloads = (d.downloads || 0) + 1;
        if (d.once) res.on('finish', () => setTimeout(() => dropRemove(d.id), 2000));
        sendFile(req, res, abs, st, 'no-store');   // 复用现有 Range/206/416/ETag
    });
}
```

```js
        'X-Accel-Buffering': 'no',

}
```

### 5.3 前端核心

```js
const CHUNK = 4 * 1024 * 1024;

async function uploadOne(file, onProgress) {
    // 1) 先建会话，服务端拿到 size/name，之后不依赖 content-length
    const meta = await (await fetch('/api/drop', {
        method: 'POST',
        headers: { 'content-type': 'application/json' },
        body: JSON.stringify({ name: file.name, size: file.size, type: file.type, ttl: 6, once: false }),
    })).json();

    // 2) 分片 PUT，409 时按服务端给的 offset 续传
    let off = 0;
    while (off < file.size) {
        const end = Math.min(off + CHUNK, file.size);
        const r = await fetch('/api/drop/' + meta.id, {
            method: 'PUT',
            headers: {
                'content-range': `bytes ${off}-${end - 1}/${file.size}`,
                'x-token': meta.token,
                'content-type': 'application/octet-stream',
            },
            body: file.slice(off, end),          // Blob.slice，零拷贝
        });
        if (r.status === 409) { off = (await r.json()).expect; continue; }
        if (!r.ok) throw new Error(await r.text());
        off = end;
        onProgress(off, file.size);
    }
    await fetch('/api/drop/' + meta.id + '/finish', { method: 'POST', headers: { 'x-token': meta.token } });
}

// 单文件上传进度（fetch 没有上传进度，必须 XHR）
function putChunkXHR(url, token, blob, range, onProgress) {
    return new Promise((ok, no) => {
        const xhr = new XMLHttpRequest();
        xhr.open('PUT', url);
        xhr.setRequestHeader('content-range', range);
        xhr.setRequestHeader('x-token', token);
        xhr.setRequestHeader('content-type', 'application/octet-stream');
        xhr.upload.onprogress = (e) => { if (e.lengthComputable) onProgress(e.loaded, e.total); };
        xhr.onload = () => ok({ status: xhr.status, text: xhr.responseText });
        xhr.onerror = () => no(new Error('network'));
        xhr.send(blob);
    });
}
```
